# AVE-2026-0045 — Tool-Retrieval Manipulation

| Field | Value |
|-------|-------|
| **AVE ID** | AVE-2026-0045 |
| **Name** | Tool-Retrieval Manipulation |
| **Aliases** | Lazy Tool Loading Attack, Tool Retrieval Starvation, Selective Tool Surfacing |
| **Category** | tool |
| **Severity** | high |
| **Status** | proven |
| **CWE** | CWE-693 (Protection Mechanism Failure), CWE-284 (Improper Access Control) |
| **Affected Frameworks** | any (agents using retrieved / selective tool loading) |
| **Detector** | `nail_monitor.detectors_v9.ToolRetrievalIntegrityDetector` |

---

## Summary

Agents increasingly cut context cost by **retrieving only the tools relevant to
the current task** (lazy / selective tool loading) instead of placing every tool
schema in the prompt — a shift that can cut agent token use dramatically. The
retrieved subset is a new attack surface: an attacker who shapes the query or
surrounding context can steer retrieval so that

- a **required** safety/approval/validation tool is never loaded (**starvation**), or
- an **unauthorised**, often high-risk, tool is pulled into the working set (**surfacing**).

No tool is poisoned and every loaded tool has clean metadata, so a full-manifest
integrity scan stays silent — it can only inspect tools that were actually loaded.

---

## Mechanism

1. The agent selects a **subset** of tools per turn, typically via semantic
   retrieval over a tool registry, rather than loading the full manifest.
2. That selection step is influenced by the **same untrusted context** the agent
   already ingests — RAG chunks, tool output, user text.
3. **Starvation:** the retriever ranks a required guard/approval/validation tool
   below the cut-off. The agent proceeds without the control and cannot fall back
   to a tool it never loaded.
4. **Surfacing:** adversarial context nudges the retriever to load a high-risk-scope
   tool (`shell`, `filesystem`, `network`, `secrets`) the task never authorised.
5. Because each loaded tool's manifest is individually clean, **manifest-integrity
   and signature checks pass** — the failure is in *what was selected*, not in the
   metadata of what was selected.

---

## Blast Radius

- **Silent bypass of tool-level safety controls.** A starved approval tool means
  privileged actions run without their gate; a surfaced high-risk tool grants
  capability outside the task's least-privilege envelope.
- **Fleet capability drift.** Semantic retrieval makes agents load divergent
  tool-sets for the *same* task — an inconsistent, unattestable capability surface
  (the tool-layer analogue of Semantic Fragmentation, AVE-2026-0037).
- **Scales with autonomy.** The more a fleet trusts retrieval to bound capability,
  the more a manipulated retrieval silently widens or narrows that bound.

---

## Defences

### 1. Tool Retrieval Integrity Monitor *(detective — implemented)*
`nail_monitor.detectors_v9.ToolRetrievalIntegrityDetector` compares the per-turn
**loaded subset** against:
- a per-task **required-tool set** — fail-closed CRITICAL on starvation;
- an **authorised least-privilege registry** — alert on surfacing, escalated to
  CRITICAL when the surfaced tool carries a high-risk scope
  (`shell / filesystem / network / database / email / secrets / payments`).

Deterministic and metadata-driven (no model calls); silent when no policy is
configured, so it does not false-fire. Wired into `NailMonitor` via
`observe_tool_retrieval(loaded_tools=…, authorized_tools=…, required_tools=…)`.

### 2. Required-Tool Fail-Closed Policy *(preventive)*
Declare the safety/approval/validation tools each task type **must** have, and
refuse to act when any is absent from the retrieved subset — rather than trusting
the retriever to have included them.

### 3. Least-Privilege Retrieval Allowlist *(mitigating)*
Bound the retrievable set to a task-scoped authorised allowlist and gate
high-risk-scope tools behind explicit authorisation, so retrieval cannot surface
capability outside the task envelope.

## Key Insight

> Manifest integrity asks "is this loaded tool honest?" Tool-retrieval integrity
> asks "were the *right* tools loaded, and only those?" Lazy loading makes the
> selection step — not the tool metadata — the control-plane surface. You cannot
> scan a tool you never loaded, so the defence must reason about the loaded subset
> against the task's required and authorised sets.
